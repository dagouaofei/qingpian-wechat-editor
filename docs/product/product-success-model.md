# 轻篇产品成功模型

> **文档角色：** 轻篇 Release 级 Outcome Goal、产品假设、成功指标、失败信号与反馈机制的**当前生效事实源**（S12-STORY-004 · **DECISION-119**）。
>
> **配套文档：** [`user-story-map.md`](user-story-map.md) — 用户旅程与 Story Map 切片

---

## 1. 为什么要加入产品成功机制

轻篇完整产品方向已在 S12-STORY-002 / S12-STORY-003 中确立，但**功能目录与 Story Map 不等于商业成功**。

每个 Release 需要回答的不只是「功能是否做完」，还包括：

- 用户是否愿意**持续使用**；
- 是否**明显省时**；
- 内容是否达到**可发布标准**；
- 内容资产是否**越用越有价值**；
- 复盘与反馈是否**影响下一轮 Backlog**。

本模型为 **S12-STORY-005**（Product Backlog 与 Release 追踪）和 **S12-STORY-008**（Release 2 路线）提供验证框架。

### 1.1 本 Story 明确不做

- 不决定 Release 2 最终范围；
- 不直接生成 Product Backlog 全量条目；
- 不开发产品代码；
- 不启动 S12-STORY-005。

---

## 2. Release 级 Outcome Goal（候选）

验证轻篇是否能帮助高频内容生产者围绕一个品牌，从灵感、选题、创作、编辑、排版到公众号发布形成**可用闭环**，并显著提升内容生产效率、成稿质量和持续复用能力。

**首要验证对象：** Product Owner 自己的高频内容运营工作（秒篇 AIPPT、AI 论文、SEO/GEO、鲁老师项目等）。

> Release 2 最终 Outcome Goal 由 **S12-STORY-008** 在 Release Planning 中确认；本 Story 提供候选。

---

## 3. 核心产品假设

| 编号 | 假设                                                           |
| ---- | -------------------------------------------------------------- |
| H01  | Product Owner 自己作为高频内容生产者，愿意持续使用轻篇生产内容 |
| H02  | 品牌资料和知识库能明显提升生成内容的贴合度                     |
| H03  | 灵感到选题闭环能减少「不知道写什么」的问题                     |
| H04  | AI 生成 + 编辑优化能减少从 0 到 1 写作时间                     |
| H05  | 排版与样式系统能让文章达到可直接发布标准                       |
| H06  | Preview / Copy 一致性是公众号场景的核心留存前提                |
| H07  | 内容资产沉淀能提升后续复用效率                                 |
| H08  | 轻量复盘能影响下一轮选题和内容计划                             |
| H09  | 高表现内容拆解与再创作可能提高短期使用吸引力                   |
| H10  | 如果产品只做单篇生成，长期价值不足                             |

---

## 4. 成功指标候选

| 维度       | 指标                                       |
| ---------- | ------------------------------------------ |
| 使用频率   | Product Owner 是否每周实际使用轻篇生产内容 |
| 闭环完成   | 是否能从品牌/灵感到公众号成稿跑通          |
| 成稿质量   | 是否达到可发布标准                         |
| 效率       | 是否比手工写作和排版明显省时               |
| 复制稳定性 | 复制到公众号是否保持样式                   |
| 内容连续性 | 是否能支持栏目、系列和多篇持续生产         |
| 资产复用   | 历史内容、案例、片段是否被复用             |
| 复盘反馈   | 数据或反馈是否改变下一轮选题               |
| 商业潜力   | 是否出现明确付费场景或可售卖包装           |
| 风险控制   | 是否避免明显洗稿、侵权、平台风险           |

---

## 5. 失败信号候选

| 维度       | 失败信号                             |
| ---------- | ------------------------------------ |
| 使用意愿   | Product Owner 自己不用或只偶尔用     |
| 内容质量   | 生成内容仍需大量重写                 |
| 排版质量   | 文章仍不像可直接发布公众号文章       |
| 复制稳定性 | 公众号复制仍频繁失真                 |
| 运营价值   | 不能解决「写什么」和「持续写」的问题 |
| 资产价值   | 历史内容没有被复用                   |
| 复盘价值   | 发布后反馈没有进入下一轮计划         |
| 产品方向   | 被单篇生成工具或洗稿工具方向带偏     |
| 商业价值   | 找不到明确愿意持续付费的用户场景     |

---

## 6. 上线反馈机制

Release 2 及后续迭代，至少记录：

- Product Owner 自己每次使用的真实流程；
- 每次从灵感到成稿耗时；
- 哪些步骤最卡；
- 哪些结果可直接使用；
- 哪些结果需要人工大改；
- 哪些内容被发布；
- 发布后的数据和反馈；
- 哪些功能影响下一轮 Backlog；
- 哪些候选功能应降级、延后或删除。

---

## 7. Backlog 调整机制

当失败信号出现或成功指标未达标时：

1. **Sprint Review / Release Review** 对照 Outcome Goal 与假设（H01–H10）复盘；
2. 将观察结果写入 Execution Evidence 与 Changelog；
3. **S12-STORY-005 及后续 Backlog 工作** 依据反馈调整 Release Backlog 优先级；
4. **S12-STORY-008** 可据此调整 Release 2 必须做 / 可以做 / 明确不做；
5. 不自动删除 Story Map 中的长期方向，但可**延后** Slice 或能力进入 Backlog 的时机。

---

## 8. 与 Release Planning、Sprint Review、Product Backlog 的关系

| 机制                 | 角色                                                            |
| -------------------- | --------------------------------------------------------------- |
| **Story Map**        | 定义用户完成任务的全景路径（见 `user-story-map.md`）            |
| **Outcome Goal**     | 定义当前 Release 要验证的商业/使用结果                          |
| **产品假设**         | 将 Outcome 分解为可检验的判断                                   |
| **成功/失败指标**    | 在 Review 中判定假设是否成立                                    |
| **Product Backlog**  | 将实现、完善、修复能力的工作排队（S12-STORY-005 建立）          |
| **Release Planning** | 从 Story Map 与成功模型中选取当前 Release 范围（S12-STORY-008） |
| **Sprint Review**    | 检查本轮交付是否推进 Outcome 与假设                             |
